How modules talk to each other (this is NOT microservices):

  Mechanism                         Used for
  --------------------------------  --------------------------------------------
  Published service interfaces      Sync reads and authorization checks
  Spring application events         Notifications / audit AFTER commit
  Kafka (optional, off by default)  Async fan-out off the request thread

Shared request gate (every tenant-scoped call):

  authenticated?
       -> which college?          (from SIGNED JWT, never from client input)
       -> is the module enabled?  (ModuleAccessGuard)
       -> has the permission?     (@PreAuthorize / classroom permission)
       -> does the resource belong to this college?  (TenantGuard)
       -> is the caller a member/owner?

2.1  COMMON  (shared infrastructure, not a business module)
--------------------------------------------------------------------------------

Package     : com.CoreService.CoreService.common
Owns        : config, context, jwt, security, redis, websocket, exception,
              entity bases, response envelope
Tables      : none (infrastructure only)

WORKING
  Cross-cutting layer every feature module depends on.
  - JwtFilter validates signature, expiry and revocation, then fills
    UserContext and CollegeContext from the signed token.
  - TenantGuard is the single ownership check. A cross-tenant hit is
    returned as 404 (not 403) so callers cannot discover other colleges.
  - RateLimitFilter uses Redis fixed-window counters (stricter on /auth).
  - WebSocket handshake is open; CONNECT must carry a valid access token.
    SUBSCRIBE is deny-by-default via WebSocketDestinationAuthorizer.
  - GlobalExceptionHandler returns a consistent error envelope with no
    stack traces.
  - BaseEntity / TenantAwareEntity / AuditableEntity are the JPA bases.

TECHNOLOGIES USED IN THIS MODULE
  Spring Security, JJWT, Redis, Spring WebSocket/STOMP, HikariCP,
  Spring Cache, Spring Async, springdoc-openapi, Jakarta Validation.

KEY PIECES
  JwtService / JwtFilter          token create + request authentication
  CollegeContext / UserContext    ThreadLocal tenant + caller
  TenantGuard                     college ownership
  SecurityConfig                  filter chain + @EnableMethodSecurity
  TokenBlacklistService           logout jti blacklist in Redis
  RateLimitFilter                 Redis RPM budgets
  RedisService                    cache, OTP, counters
  WebSocketConfig                 STOMP broker at /ws
  ApiResponse / PageResponse      HTTP envelope
  DomainEvent                     event contract for listeners

2.2  AUTH
--------------------------------------------------------------------------------

Package     : com.CoreService.CoreService.auth
API         : /api/v1/auth
Tables      : auth_refresh_tokens
Module code : (always on — identity is not toggleable)

WORKING
  Issues and rotates sessions. Login checks user id + BCrypt password,
  then builds a JWT that already contains roles, permissions and the
  college's enabled modules. Refresh tokens are opaque rows in MySQL
  and rotate on every use. Logout deletes the refresh token AND
  blacklists the access-token jti in Redis until it expires.
  Forgot-password always reports success (no user-id enumeration).
  OTP lives in Redis for 5 minutes. Changing or resetting a password
  revokes every refresh token for that user.

TECHNOLOGIES USED
  Spring Security, BCrypt, JJWT, MySQL (refresh tokens), Redis (OTP,
  reset window, access-token blacklist), Jakarta Validation.

ENDPOINTS
  POST /login
  POST /refresh  (also /refreshToken)
  POST|PUT /logout
  POST /forgot-password
  POST /verify-otp
  POST /reset-password
  POST /change-password

FLOW
  Client
    -> POST /auth/login { userId, password }
    -> AuthService: load user, BCrypt match, reject if deactivated
    -> load roles + permissions + enabled modules
    -> JwtService signs access token (sub, collegeId, roles, permissions,
       modules, jti)
    -> RefreshTokenService stores opaque refresh token in MySQL
    -> LoginResponse { accessToken, refreshToken, user profile }

  Later requests
    Authorization: Bearer <access>
    -> RateLimitFilter -> JwtFilter (sig / exp / blacklist)
    -> UserContext + CollegeContext set
    -> Controller / @PreAuthorize / service

  Logout
    -> delete refresh token row
    -> blacklist access jti in Redis until expiry

2.3  COLLEGE  (tenant)
--------------------------------------------------------------------------------

Package     : com.CoreService.CoreService.College
API         : /api/v1/college
Tables      : colleges
Module code : platform-level (MAIN_ADMIN)

WORKING
  A college is a tenant. MAIN_ADMIN provisions a college in one call:
  college row, default roles, first COLLEGE_ADMIN, and enabled modules.
  The admin temporary password is returned once and cannot be fetched
  again. Deleting a college cascades to everything it owns
  (ON DELETE CASCADE). College users read/update only their own tenant
  via JWT collegeId. MAIN_ADMIN may target a tenant with X-College-Id.

TECHNOLOGIES USED
  Spring Web MVC, Spring Data JPA, MySQL, Spring Security
  (@PreAuthorize hasRole MAIN_ADMIN / UPDATE_SETTINGS), Flyway V1.

ENDPOINTS
  POST   /                    provision college          MAIN_ADMIN
  GET    /allCollege          list tenants               MAIN_ADMIN
  GET    /search              search name/university/city MAIN_ADMIN
  GET    /{collegeId}         read any college           MAIN_ADMIN
  DELETE /{collegeId}         delete tenant + owned data MAIN_ADMIN
  GET    /myCollege           current tenant
  PUT    /                    update own college         UPDATE_SETTINGS

FLOW
  MAIN_ADMIN
    -> POST /college
    -> CollegeService.createCollege
         1. insert colleges
         2. seed COLLEGE_ADMIN / TEACHER / STUDENT roles
         3. create first admin user + assign role
         4. enable requested system modules on college_modules
    -> return CollegeProvisioningResult (admin password once)

2.4  USER
--------------------------------------------------------------------------------

Package     : com.CoreService.CoreService.user
API         : /api/v1/users
Tables      : users
Module code : USER_MANAGEMENT

WORKING
  Identity accounts. user_id is a natural key (not a UUID). college_id
  is nullable so MAIN_ADMIN sits above any tenant. Passwords are BCrypt
  hashed and never serialized. College admins create, activate,
  deactivate, search and delete users inside their college. Password
  change goes through this module or Auth, and both revoke sessions.

TECHNOLOGIES USED
  Spring Data JPA, BCrypt, MySQL, Spring Security (CREATE_USER,
  VIEW_USER, UPDATE_USER, DELETE_USER, VIEW_ALL_COLLEGE_USER,
  DELETE_ALL_COLLEGE_USERS).

ENDPOINTS
  POST   /                      create user
  GET    /me                    own profile
  GET    /{userId}              MAIN_ADMIN lookup
  GET    /all                   MAIN_ADMIN list
  GET    /college               users of current college
  GET    /search?keyword=
  GET    /checkUser?userId=
  PATCH  /byUser                self update
  PATCH  /byAdmin               college-admin update
  PATCH  /{userId}/activate
  PATCH  /{userId}/deactivate
  PATCH  /changePassword
  DELETE /{userId}
  DELETE /all                   all users of college

FLOW
  COLLEGE_ADMIN (CREATE_USER)
    -> POST /users
    -> UserService hashes password, binds college_id from CollegeContext
    -> persist users
    -> Role module can then assign TEACHER / STUDENT / custom roles

2.5  ROLE
--------------------------------------------------------------------------------

Package     : com.CoreService.CoreService.role
API         : /api/v1/roles
Tables      : roles, user_roles
Module code : USER_MANAGEMENT

WORKING
  Dynamic RBAC. Platform roles (MAIN_ADMIN, COLLEGE_ADMIN, TEACHER,
  STUDENT) are seeded. A college can add its own roles. Assigning a
  role to a user writes user_roles. The next login (or token refresh)
  puts those roles and their permissions into the JWT.

TECHNOLOGIES USED
  Spring Data JPA, MySQL unique (college_id, role_name), Spring Security
  (CREATE_ROLE, VIEW_ROLE, UPDATE_ROLE, DELETE_ROLE, ASSIGN_ROLE,
  REMOVE_ROLE).

ENDPOINTS
  POST   /                         create role
  GET    /                         list roles of college
  GET    /{roleId}
  PUT    /{roleId}
  DELETE /{roleId}
  GET    /exists/{roleName}
  POST   /{roleId}/users/{userId}  assign
  DELETE /{roleId}/users/{userId}  unassign
  GET    /{roleId}/users
  GET    /users/{userId}
  DELETE /users/{userId}           strip all roles

FLOW
  Admin creates role
    -> RoleService persists roles (college-scoped)
    -> Permission module attaches permission codes
    -> POST /roles/{roleId}/users/{userId}
    -> user_roles row
    -> next JWT contains the new role + permissions

2.6  PERMISSION
--------------------------------------------------------------------------------

Package     : com.CoreService.CoreService.Permission
API         : /api/v1/permission
              /api/v1/rolePermission
Tables      : permissions, role_permissions
Module code : USER_MANAGEMENT

WORKING
  Catalogue of permission codes (CREATE_USER, ASSIGNMENT_GRADE, ...).
  MAIN_ADMIN owns the catalogue. College admins attach codes to roles
  (single, multiple, or replace-all). Controllers assert them with
  @PreAuthorize("hasAuthority('...')"). Feature services also check
  classroom-level permissions on top of these.

TECHNOLOGIES USED
  Spring Data JPA, MySQL, Spring method security, seeded catalogue
  via CommandLineRunner (kept in sync with Permissions.java).

ENDPOINTS  (/permission)
  POST   /addPermission              MAIN_ADMIN
  DELETE /{permissionCode}           MAIN_ADMIN
  GET    /all
  GET    /search?keyword=
  GET    /exists/{permissionCode}

ENDPOINTS  (/rolePermission)
  POST   /{roleId}/permission/{permissionId}
  POST   /role/{roleId}/multiple-permissions
  PUT    /{roleId}/permissions                 replace set
  GET    /role/{roleId}
  GET    /permission/{permissionId}
  GET    /exists/{permissionId}/role/{roleId}
  DELETE /{permissionId}/role/{roleId}

FLOW
  MAIN_ADMIN seeds / adds permission
    -> College admin maps it onto a role
    -> user with that role logs in
    -> JWT permissions[] includes the code
    -> @PreAuthorize allows or denies the endpoint

  permissions CLASSROOM_CREATE / UPDATE / DELETE / VIEW /
  MEMBER_MANAGE / PERMISSION_MANAGE.

FLOW

2.17  CHAT
--------------------------------------------------------------------------------

Package     : com.CoreService.CoreService.chat
API         : /api/v1/chat
STOMP       : /app/chat/send , /app/chat/join
              subscribe /topic/chat/{chatRoomId}
Tables      : chat_rooms, chat_participants, chat_messages
Events      : ChatMessageSentEvent
Module code : CHAT

WORKING
  Two room types: classroom room (get-or-create per classroom) and
  direct room (pair of users). REST covers history, unread, read
  receipts, permission mode, and a fallback send for clients without
  a live socket. Live send uses STOMP. Sender identity is taken from
  the session principal, never from the payload. File messages store
  file_id only. Permission mode on a room (who may post) is owned
  here and checked against classroom role.

TECHNOLOGIES USED
  Spring Web MVC, Spring WebSocket + STOMP, SimpMessagingTemplate,
  Spring Data JPA, MySQL V7, FileLookupService, ClassroomAccessService,
  permissions CHAT_VIEW / CHAT_SEND.

ENDPOINTS
  POST   /direct-rooms
  POST   /classroom-rooms/{classroomId}
  GET    /rooms/{chatRoomId}/messages
  POST   /rooms/{chatRoomId}/read
  GET    /unread-counts
  POST   /messages                              REST fallback send
  PATCH  /rooms/{chatRoomId}/permission-mode
  DELETE /messages/{messageId}

STOMP
  /app/chat/send   -> persist + broadcast /topic/chat/{roomId}
  /app/chat/join   -> presence / participant check
  errors           -> /user/queue/errors  (sender only)

FLOW
  Client CONNECT /ws + JWT
    -> SUBSCRIBE /topic/chat/{roomId}  (authorizer: must be participant)
    -> SEND /app/chat/send { chatRoomId, content, messageType, fileId }
    -> ChatWebSocketController asserts CHAT_SEND on principal
    -> ChatService persists chat_messages, updates unread
    -> broadcast to room
    -> ChatMessageSentEvent -> optional notification for offline users

2.18  MEETING  (video conference)
--------------------------------------------------------------------------------

Package     : com.CoreService.CoreService.meeting
API         : /api/v1/meetings
STOMP       : /app/meeting/signal
              subscribe /topic/meeting/{meetingId}
              /user/queue/signal
Tables      : meetings, meeting_participants
Events      : MeetingScheduledEvent, MeetingStartedEvent
Module code : VIDEO_CONFERENCE

WORKING
  Backend owns scheduling, participants, lifecycle and WebRTC
  signaling ONLY. It never carries audio or video.
  Lifecycle is separate endpoints (not a free-form status field):
  scheduled -> started -> ended, or cancelled.
  Join returns a MeetingJoinResponse (join URL / room credentials
  from VideoConferenceProvider). Default provider is
  InternalWebRtcProvider. Signaling frames (OFFER, ANSWER,
  ICE_CANDIDATE) are relayed to a target peer; JOIN/LEAVE go to
  the meeting topic. Every signal frame is re-authorized
  (participant must still be active).

TECHNOLOGIES USED
  Spring Web MVC, Spring WebSocket + STOMP, WebRTC signaling
  (SDP / ICE relay), VideoConferenceProvider SPI (swap Jitsi /
  LiveKit / Agora without touching business code), MySQL V7,
  ClassroomAccessService, permissions MEETING_CREATE / UPDATE /
  JOIN / VIEW.

ENDPOINTS
  POST /                         schedule
  PUT  /{meetingId}
  POST /{meetingId}/cancel
  POST /{meetingId}/start
  POST /{meetingId}/end
  POST /{meetingId}/join
  POST /{meetingId}/leave
  GET  /{meetingId}
  GET  /upcoming
  GET  /classrooms/{classroomId}

STOMP
  /app/meeting/signal  { meetingId, type, targetUserId, payload }
    OFFER / ANSWER / ICE_CANDIDATE -> /user/queue/signal of peer
    JOIN / LEAVE                   -> /topic/meeting/{meetingId}

FLOW
  Teacher schedules meeting on classroom
    -> MeetingScheduledEvent -> notify members
  Host starts
    -> MeetingStartedEvent -> notify
  Participant POST /meetings/{id}/join
    -> provider issues join info
    -> browser WebRTC
    -> signaling through /app/meeting/signal
    -> media P2P or SFU, never through this service

2.19  NOTIFICATION

Package     : com.CoreService.CoreService.notification
API         : /api/v1/notifications
Tables      : notifications, device_tokens
Published   : NotificationDispatcher
STOMP       : /user/queue/notifications
Module code : NOTIFICATION

WORKING
  In-app inbox driven by domain events. NotificationEventListener is
  @TransactionalEventListener + @Async: a rolled-back assignment never
  produces a notification, and ThreadLocal is rebuilt from the event

  be plugged in). Device tokens are registered per platform.

TECHNOLOGIES USED

  optional Kafka + Redis dedup, STOMP user queues,
  PushNotificationProvider SPI, permissions NOTIFICATION_VIEW.

ENDPOINTS
  GET    /                         my inbox (unreadOnly)
  GET    /unread-count
  PATCH  /{notificationId}/read
  PATCH  /read-all
  POST   /device-tokens
  GET    /device-tokens
  PATCH  /device-tokens/{id}/deactivate
  DELETE /device-tokens/{id}

  AttendanceMarked

  AssignmentPublished, AssignmentSubmitted, AssignmentGraded
  MaterialUploaded

2.20  FILE

Package     : com.CoreService.CoreService.file
API         : /api/v1/files
Tables      : stored_files
Published   : FileStorageService, FileLookupService
Module code : used by ASSIGNMENT, STUDY_MATERIAL, CHAT (not toggled itself)

WORKING

TECHNOLOGIES USED

  (STORAGE_LOCAL_PATH), MySQL V6, TenantAware metadata.

  GET    /{fileId}         download
  GET    /{fileId}/metadata

FLOW
  Client multipart POST /files
    -> validate size / type
    -> provider.store(bytes)
    -> insert stored_files (college_id, path, contentType, size)
    -> return StoredFileRef
  Assignment / Material / Chat
    -> FileLookupService.assertOwned(fileId, collegeId)
    -> save file_id on their row

2.22  AUDIT
--------------------------------------------------------------------------------

Package     : com.CoreService.CoreService.audit
API         : /api/v1/audit
Tables      : audit_logs
Published   : AuditRecorder
Module code : (college-admin / platform)

WORKING
  Append-only trail of sensitive actions. Listeners are
  @TransactionalEventListener + @Async and write with
  REQUIRES_NEW so a failed audit insert cannot roll back business
  data, and a failed business txn never writes an audit row.
  user_id has NO foreign key — the trail outlives the account.
  Search by action, resourceType, userId, from/to.

TECHNOLOGIES USED
  Spring Data JPA, MySQL V5, Spring events, REQUIRES_NEW
  transactions, permission AUDIT_VIEW.

ENDPOINTS
  GET /?action=&resourceType=&userId=&from=&to=&page=&size=

FLOW
  Service records via AuditRecorder or domain event
    -> AuditEventListener after commit
    -> new transaction insert audit_logs
    -> COLLEGE_ADMIN searches GET /audit

================================================================================
5. END-TO-END PLATFORM FLOW
================================================================================

This is the full path from an empty database to a student submitting
work and sitting in a live class.


STEP A — BOOTSTRAP
  Application starts
    -> Flyway applies V1..V7
    -> seed permissions, system_modules, MAIN_ADMIN role
    -> create platform admin (password logged once if not set)
    -> Redis + (optional) Kafka connect
    -> HTTP :8082 and STOMP /ws up


STEP B — PROVISION A COLLEGE
  MAIN_ADMIN POST /auth/login
    -> JWT (no collegeId)
  MAIN_ADMIN POST /college
    -> college + default roles + COLLEGE_ADMIN user + modules
  MAIN_ADMIN POST /college-modules  (or included in provision)
    -> enable CLASSROOM, ASSIGNMENT, ATTENDANCE, CHAT, ...


STEP C — COLLEGE ADMIN SETS UP PEOPLE AND STRUCTURE
  Login as COLLEGE_ADMIN  (X-College-Id not needed; college is in JWT)

  Academic
    departments -> programs -> current session -> semesters -> subjects

  Users
    POST /users  (teachers, students) + assign roles
    POST /teachers  + assign subjects
    POST /students  (link user to program/semester)

  Classrooms
    POST /classrooms
    POST /{id}/students   and   /{id}/teachers
    PUT  /{id}/permissions


STEP D — EVERY SUBSEQUENT HTTP REQUEST
  Client
    -> RateLimitFilter (Redis)
    -> JwtFilter (signature, expiry, jti not blacklisted)
    -> UserContext + CollegeContext from token
    -> @PreAuthorize (role / permission)
    -> Controller (DTO only)
    -> Service
         ModuleAccessGuard.assertModuleEnabled(...)
         TenantGuard.assertSameCollege(...)
         ClassroomAccessService.assertPermission(...)   if room-scoped
         business rules + @Transactional
         persist via repository (always filter college_id)
         publish DomainEvent
    -> ApiResponse
  After commit
    -> NotificationEventListener (@Async)
    -> AuditEventListener (@Async, REQUIRES_NEW)
    -> optional Kafka


STEP E — TEACHING LOOP (one classroom)
  Syllabus     create units/topics, mark progress
  Material     POST /files then POST /materials
  Assignment   create -> publish -> student submit -> grade
  Attendance   create session -> mark -> lock
  Announcement create -> publish  (classroom or college)
  Each of these emits events -> in-app notification
    (+ STOMP /user/queue/notifications)


STEP F — REAL-TIME CHAT
  Client opens WebSocket /ws
    -> CONNECT with Bearer JWT  (WebSocketAuthChannelInterceptor)
    -> REST POST /chat/classroom-rooms/{classroomId}
    -> SUBSCRIBE /topic/chat/{roomId}
         WebSocketDestinationAuthorizer: participant + same college
    -> SEND /app/chat/send
    -> persist + broadcast + unread counters


STEP G — LIVE MEETING
  Teacher POST /meetings  (schedule)  -> notify
  Teacher POST /meetings/{id}/start   -> notify
  Each member POST /meetings/{id}/join
    -> VideoConferenceProvider returns join info
  Browsers exchange OFFER / ANSWER / ICE via /app/meeting/signal
  Media flows peer-to-peer (or external SFU), not through core-service
  Host POST /meetings/{id}/end


STEP H — DASHBOARDS AND AUDIT
  Student   GET /dashboard/student     assignments due, attendance %,
                                       unread, upcoming meetings
  Teacher   GET /dashboard/teacher     owned rooms, pending grades
  Admin     GET /dashboard/college-admin
            GET /audit?action=&from=&to=


STEP I — LOGOUT / PASSWORD CHANGE
  POST /auth/logout
    -> refresh token deleted
    -> access jti blacklisted in Redis
  Password change / reset
    -> all refresh tokens for that user deleted
    -> old access tokens die at expiry or on blacklist

7. SECURITY AND TENANCY (applies to all modules)
================================================================================

  Authentication     JWT access (15 min) + rotating refresh (7 days, MySQL)
  Authorization      dynamic RBAC  Role -> RolePermission -> Permission
  Module gating      college_modules.enabled via ModuleAccessGuard + Redis cache
  Classroom gating   ClassroomAccessService.assertPermission
  Tenant isolation   college_id from JWT; repositories filter; TenantGuard
                     cross-tenant = 404
  MAIN_ADMIN         no college; optional header X-College-Id
  WebSocket          CONNECT authenticated; SUBSCRIBE deny-by-default
  Rate limit         Redis, 300 rpm general, 20 rpm on /api/v1/auth/**
  Passwords          BCrypt; never in JSON
  Errors             no stack traces, no internal messages
